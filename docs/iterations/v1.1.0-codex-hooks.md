# v1.1.0 — Codex Hook Minimum Viable Loop

- **Status:** Accepted MVP
- **Design approved:** 2026-07-31
- **Implementation verified:** 2026-07-31
- **Target:** Apple Silicon macOS

## User Problem

The existing pet reacts to CodeBuddy but cannot represent the activity of a Codex coding session. A Codex user therefore receives no ambient status feedback from Blueberry.

## Objective

Replace the CodeBuddy event source with Codex Hooks and prove that Codex lifecycle events can safely, privately, and reliably drive the existing pet animations.

## Hypothesis

If Blueberry can translate Codex lifecycle events into immediate ambient animations, a user can understand whether Codex is thinking, working, waiting for approval, finished, or inactive without repeatedly reopening the Codex interface.

v1.1.0 tests event-path reliability. It does not test whether additional animation variety improves comprehension.

## In Scope

- A Python standard-library Codex Hook adapter.
- A normalized Blueberry event protocol.
- A loopback `POST /event` endpoint.
- A pure event-to-state router.
- Existing Idle, Thinking, Working, Attention, Happy, and Sleeping visuals.
- Contract, routing, integration, degradation, end-to-end, and arm64 packaging tests.
- Updated Codex installation and removal documentation.

## Out of Scope

- New animation assets.
- Apple Music.
- Water and break reminders.
- LLM, RAG, chat, or memory.
- Tool success/failure classification.
- Subagent visuals.
- Codex control or permission decisions.
- Intel Mac and public distribution requirements.

## Confirmed Product Decisions

- Reuse existing animations until the Codex path passes acceptance.
- Preserve semantic event distinctions even when events share an animation.
- Keep the Python process short-lived rather than introducing a persistent backend.
- Collect only event identity and allowlisted metadata.
- Treat Blueberry as observational: its failure must never become Codex failure.
- Exclude compact and subagent events until the product has an intentional visual treatment for them.

## Confirmed Mapping

| Codex condition | Semantic event | Temporary visual |
|---|---|---|
| Session starts, resumes, or clears | `session.started` | Idle |
| User submits a prompt | `turn.prompt_submitted` | Thinking |
| Tool begins | `tool.started` | Working |
| Tool finishes | `tool.finished` | Working |
| Permission is requested | `permission.requested` | Attention |
| Turn stops normally | `turn.finished` | Happy |
| Main session ends | `session.ended` | Sleeping |

## Validation

The iteration is accepted only after automated contract and routing tests, Hook-to-HTTP integration tests, real Codex smoke tests, privacy assertions, failure-mode tests, latency measurements, and an Apple Silicon macOS build all pass.

## Acceptance Result

The MVP was accepted on 2026-08-01. The Hook was installed in the real user Codex configuration, all seven handlers were reviewed and trusted through `/hooks`, and fresh Codex sessions visibly exercised Thinking, Working, Attention, and Sleeping reactions. Real event diagnostics also confirmed Stop and SessionEnd delivery without collecting private Hook payload content.

Acceptance uncovered and fixed the `Stop → SessionEnd` race: Blueberry now completes the Happy reaction before entering Sleeping. The final regression suite passed 39 Node tests and 10 Python tests, and the corrected Apple Silicon application was rebuilt and installed.

Unsigned/unnotarized public distribution and Intel Mac support remain out of scope; they do not block the local macOS MVP.
