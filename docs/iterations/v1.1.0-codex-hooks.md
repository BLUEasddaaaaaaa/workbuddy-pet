# v1.1.0 — Codex Hook Minimum Viable Loop

> **Current status (2026-08-09):** The frozen v1.1.0 candidate passed source automation, clean arm64 packaging, artifact identity, audited installation, two-round installed-runtime acceptance, real single-conversation Codex Hook acceptance, and failure/rollback acceptance. GitHub publication is still pending. The app is unsigned and unnotarized, so the release must be presented as an Apple Silicon test/pre-release rather than a publicly safe macOS distribution. Historical failed and superseded attempts remain below as context.

- **Status:** Locally accepted release candidate; GitHub publication pending
- **Design approved:** 2026-07-31
- **Latest release-candidate verification:** 2026-08-09
- **Target:** Apple Silicon macOS

## User Problem

The existing pet reacts to CodeBuddy but cannot represent the activity of a Codex coding session. A Codex user therefore receives no ambient status feedback from Blueberry.

## Objective

Replace the CodeBuddy event source with Codex Hooks and prove that Codex lifecycle events can safely, privately, and reliably drive the existing pet animations.

## Hypothesis

If Blueberry can translate Codex lifecycle events into immediate ambient animations, a user can understand whether Codex is thinking, working, waiting for approval, finished, or inactive without repeatedly reopening the Codex interface.

v1.1.0 tests event-path reliability. It does not test whether additional animation variety improves comprehension.

## In Scope

- A Python standard-library Codex Hook adapter.
- A normalized Blueberry event protocol.
- A loopback `POST /event` endpoint.
- A pure event-to-state router.
- Existing Idle, Thinking, Working, Attention, Happy, and Sleeping visuals.
- Contract, routing, integration, degradation, end-to-end, and arm64 packaging tests.
- Updated Codex installation and removal documentation.

## Out of Scope

- New animation assets.
- Apple Music.
- Water and break reminders.
- LLM, RAG, chat, or memory.
- Tool success/failure classification.
- Subagent visuals.
- Codex control or permission decisions.
- Intel Mac and public distribution requirements.

## Confirmed Product Decisions

- Reuse existing animations until the Codex path passes acceptance.
- Preserve semantic event distinctions even when events share an animation.
- Keep the Python process short-lived rather than introducing a persistent backend.
- Collect only event identity and allowlisted metadata.
- Treat Blueberry as observational: its failure must never become Codex failure.
- Exclude compact and subagent events until the product has an intentional visual treatment for them.

## Confirmed Mapping

| Codex condition | Semantic event | Temporary visual |
|---|---|---|
| Session starts, resumes, or clears | `session.started` | Idle |
| User submits a prompt | `turn.prompt_submitted` | Thinking |
| Tool begins | `tool.started` | Working |
| Tool finishes | `tool.finished` | Working |
| Permission is requested | `permission.requested` | Attention |
| Turn stops normally | `turn.finished` | Happy |
| Main session ends | `session.ended` | Idle |

`SessionEnd` ends the active Codex state and returns Blueberry to awake Idle; it does not trigger Sleeping. Sleeping is entered only through the local mouse-idle timeout.

## Historical Acceptance Result — 2026-08-01

The MVP was accepted on 2026-08-01. The Hook was installed in the real user Codex configuration, all seven handlers were reviewed and trusted through `/hooks`, and fresh Codex sessions visibly exercised Thinking, Working, Attention, and Sleeping reactions. Real event diagnostics also confirmed Stop and SessionEnd delivery without collecting private Hook payload content.

## Runtime Stabilization Addendum — 2026-08-01

Two additional controlled runtime rounds confirmed that the Hook adapter returns quickly and successfully, but also reproduced persistent Working under concurrent Codex activity. Blueberry currently collapses all tasks into one renderer state, discards `session_id`, and restarts transient animation timers on later events. The result is visually interrupted or masked behavior even though Hook transport is functioning.

The detailed evidence is recorded in [v1.1.0 Two-Round Runtime Hook Test](evidence/v1.1.0-runtime-two-round-test-2026-08-01.md).

The confirmed stabilization direction is a lightweight session-aware state coordinator with:

- one state per Codex session;
- priority-based resolution;
- same-state deduplication;
- minimum display durations;
- at most one pending candidate;
- recomputation from live sessions after a hold or session end.

This is an independent, reduced implementation inspired by the state-management ideas in Clawd on Desk. Blueberry will not copy its AGPL-3.0 implementation and will not adopt its complete complexity in v1.1.0.

The approved architecture, transition policy, recovery behavior, and test gates are documented in [Blueberry v1.1.0 State Arbitration Design](../superpowers/specs/2026-08-01-blueberry-v1.1.0-state-arbitration-design.md).

**Historical decision at this stage:** hold the stable GitHub release until the arbitration change was implemented and the two-round plus overlapping-session runtime acceptance passed.

## State Arbitration Acceptance — 2026-08-01

The lightweight coordinator, renderer deduplication, and renderer-readiness bridge are implemented. The readiness bridge was added after review exposed a startup race: a coordinator state could be emitted before renderer IPC delivery was attached. It now buffers only the latest approved state and replays it once after attachment.

Fresh verification passed 77 JavaScript tests, 10 Python tests, and the arm64 build. All 22 measured installed Hook processes completed below 200 ms. However, installed UI acceptance found a renderer-policy mismatch: an Attention animation can time out locally to Idle while the deduplication policy still remembers Attention, causing the next legitimate Permission reaction to be suppressed.

Detailed commands, timings, package evidence, reproduction, and limitations are recorded in [v1.1.0 State Arbitration Acceptance](evidence/v1.1.0-state-arbitration-acceptance.md).

**Historical decision from this acceptance attempt:** stabilization remained in progress and the stable GitHub release stayed on hold pending a fresh complete run after the renderer visible-state mismatch was fixed.

### Re-acceptance after the renderer fix

The follow-up implementation separates candidate probing from committing the actual visual state: the external policy records a state only after the renderer performs the transition, and renderer-owned transitions report their actual visual state back to the ledger. The readiness bridge continues to buffer the latest approved state until renderer delivery is attached.

Fresh automated verification at `ef95df5` passed 80 JavaScript tests, 10 Python tests, and 43 focused policy/wiring tests, and a new arm64 package was built and installed. The installed-app gate did not obtain positive Attention evidence: a first diagnostic Attention request returned HTTP 200 while the Computer Use capture showed Idle, including during one isolated run with the installed Hook adapter temporarily unavailable. Computer Use capture timing and observer effects prevent treating this as conclusive proof that the renderer fix failed, but the required visual proof is absent. No production code was changed during re-acceptance, and later runtime scenarios were stopped by design.

That blocked result is retained as test history. A subsequent clean-room package run removed the old `dist`, rebuilt from source, byte-compared five critical files before and after installation, and used CDP rather than Computer Use to inspect the installed renderer. It directly proved `Attention → Idle → Attention`, plus a unique canonical Permission event. Fresh totals were 80/80 JavaScript and 10/10 Python; all 16 installed adapter events stayed below 200 ms.

**Historical decision from that superseded implementation:** v1.1.0 interaction stabilization was accepted for local macOS use, and the stable source release was considered able to proceed with an unsigned/unnotarized limitation. The current 2026-08-08 status at the top of this document supersedes that conclusion.

## Renderer Controller Worktree Acceptance — 2026-08-08

The current single-authority Renderer controller passed its simulated worktree runtime gate at source commit `3253e6e`. Fresh suites passed 74/74 JavaScript and 10/10 Python tests. A default launch exposed no debug facade; an explicit `BLUEBERRY_ACCEPTANCE=1` launch exposed only the immutable read-only snapshot facade.

Two complete rounds through the real repository Python adapter produced the same visible order, `Idle → Thinking → Working → Attention → Happy → Idle`. CDP snapshots and same-expression DOM visibility showed 2000 ms Thinking, 1000 ms Working, and 2000 ms Attention/Happy absolute protection intervals; PostToolUse did not restart Working; protected transitions remained pending; one-shots returned to the latest logical Idle without stale replay. Real local mouse inactivity produced Sleeping, and a valid Hook immediately woke it to its mapped Thinking state.

Detailed commands, process ownership, adapter measurements, timing evidence, evidence-layer limits, and cleanup are recorded in [v1.1.0 Renderer Controller Worktree Acceptance](evidence/v1.1.0-renderer-controller-acceptance-2026-08-08.md).

This result closes only the worktree runtime gate. `Stop → Happy` remains a temporary v1.1.0 mapping; permission resolution/re-reminders remain v1.2.0 work; first-pixel acknowledgement is absent; Renderer reload returns to Idle; installed-package identity and release readiness remain separate, unproven gates.
