# Blueberry v1.2.0 Product Roadmap

- **Status:** Planned; no implementation started
- **Prerequisite:** Complete v1.1.0 rename, packaging, real Codex Hook installation, and acceptance
- **Theme:** Make Codex activity easier to understand through more specific Blueberry behavior

## 1. Product Objective

v1.1.0 proves the minimum path:

`Codex Hook → privacy filter → Blueberry event → existing animation`

v1.2.0 should improve the meaning of those reactions. A user should be able to glance at Blueberry and understand what kind of Codex activity is happening without reading command, code, prompt, path, or tool-output content.

## 2. Candidate Hook Behaviors

### Newly connected lifecycle events

| Codex event | Product meaning | Candidate Blueberry behavior |
|---|---|---|
| `PreCompact` | Codex is about to organize a long context | Gather papers, sort notes, pack a memory folder |
| `PostCompact` | Context organization finished | Close the folder, wipe sweat, return to work |
| `SubagentStart` | Codex called another agent for help | Summon a small Blueberry helper or create a clone |
| `SubagentStop` | A subagent finished | Helper returns a report, high-fives, then leaves |
| `SessionStart: compact` | Codex continues after compaction | Reopen the organized folder and resume work |

### More specific behavior from existing Hooks

| Existing event or field | Safe distinction | Candidate Blueberry behavior |
|---|---|---|
| `PreToolUse` / `PostToolUse` with `Bash` | Terminal activity | Type at a terminal or wear work headphones |
| `PreToolUse` / `PostToolUse` with `apply_patch` | File editing | Repair with a hammer or paint with a brush |
| `PreToolUse` / `PostToolUse` with an MCP tool | External service activity | Use a radio, telephone, or antenna |
| `PreToolUse` with `Agent` | Agent delegation | Call a small Blueberry helper |
| `PreToolUse` with `update_plan` | Planning activity | Read a checklist and tick an item |
| `PostToolUse` with a safe derived failure status | Tool did not finish normally | Look confused, inspect the result, then retry |
| `SessionStart.source` | `startup`, `resume`, `clear`, or `compact` | Wake up, reopen notes, erase a board, or resume after organizing |
| `permission_mode` | Codex operating mode | Show a planning board, normal work pose, or focused-work pose |

The adapter must keep using an allowlist. Tool names and lifecycle states may enter the Blueberry event protocol; raw prompts, commands, code, paths, transcripts, tool input/output, and final messages must not.

## 3. Permission Reminder Research

`PermissionRequest` fires when Codex is about to ask the user for approval. It does not repeatedly fire merely because the user has not answered, and the current Hook interface has no dedicated `PermissionResolved` event.

Three reminder approaches should be evaluated:

### A. One Hook, one reminder

Blueberry reacts once when `PermissionRequest` arrives and stays in the attention state until another ordinary event changes the state.

- Lowest complexity
- Appropriate for v1.1.0 MVP
- Does not actively remind an absent user again

### B. Local reminder timer with inferred resolution — recommended for v1.2.0 research

Blueberry starts a local timer after `PermissionRequest`. If the attention state has not been cleared, it plays a gentler reminder again. It may infer resolution from a matching tool completion, a new turn, `Stop`, `SessionEnd`, or a direct user acknowledgement on Blueberry.

- Moderate implementation difficulty
- Does not require reading private content
- Needs explicit timeout, repeat limit, quiet period, and clearing rules
- Inference can be imperfect when a request is denied or Codex follows an uncommon path

### C. Observe Codex interface state

Blueberry reads the Codex window or accessibility state to determine whether the approval prompt is still visible.

- Potentially more precise for the visible app
- Fragile across Codex UI changes
- Requires additional macOS permissions and creates a larger privacy surface
- Not recommended for the near-term roadmap

Before approach B is implemented, v1.2.0 design should decide:

- first repeat delay;
- maximum repeat count;
- quiet hours and sound policy;
- which events clear the pending-permission state;
- whether clicking Blueberry means “remind me later” or “I have seen it”;
- how to prevent repeated reminders from becoming annoying.

## 4. Meaning of `permission_mode`

`permission_mode` is metadata included with several Hook events. It describes the current Codex permission/working mode; it is not a separate Hook and does not mean that an approval request is currently visible.

The [Codex Hooks documentation](https://learn.chatgpt.com/docs/hooks#common-input-fields) currently lists:

| Value | Product interpretation |
|---|---|
| `default` | Normal Codex workflow |
| `acceptEdits` | Edits may proceed with reduced interruption |
| `plan` | Codex is planning rather than directly implementing |
| `dontAsk` | Codex should avoid asking for additional approval |
| `bypassPermissions` | Permission checks are bypassed for the current run |

Blueberry may use this field for subtle visual context, but `PermissionRequest` remains the event that means the user actually needs to act.

## 5. Agreed Iteration Direction

| Version | Primary outcome |
|---|---|
| v1.1.0 | Minimum viable Codex-to-Blueberry reaction loop plus lightweight session-aware state coordination |
| v1.2.0 | Add states gradually: tool-type differentiation, context-compaction behavior, permission-reminder research, and safer success/failure expression |
| v1.3.0 | Evolve the coordinator for richer multi-window/multi-task behavior and multi-agent visualization using small Blueberry helpers |
| v1.4.0 and later | macOS activity awareness and companion behaviors such as music headphones, idle sleep, water reminders, and break reminders |

The evolution principle is confirmed: v1.1.0 implements only the lightweight coordinator needed by Blueberry's current six states. Later versions may progressively adopt mature ideas such as completion debounce, one-shot restoration, and theme-defined timing when additional states or concurrent windows create a demonstrated need. The exact scope of each version will still pass a separate design review; this roadmap records direction, not a promise that every candidate ships in one release.

## 6. Preliminary Acceptance Principles

- A user can distinguish major tool categories without opening Codex.
- Compaction has a visible start and finish sequence.
- Added events do not expose private Hook payload content.
- Missing or delayed Hooks do not leave Blueberry permanently stuck.
- Permission reminders are useful without becoming repetitive or coercive.
- New behavior remains observational and cannot block or alter Codex.
