# v1.1.0 Two-Round Runtime Hook Test

- **Executed:** 2026-08-01
- **Target:** `/Applications/Blueberry.app` 1.1.0
- **Purpose:** Reproduce reports of delayed reactions, stutter, and interrupted animations
- **Decision:** Hook transport passes; concurrent visible-state behavior fails

## Test Design

Two controlled rounds invoked the installed adapter at:

```text
~/Library/Application Support/Blueberry/hooks/codex_hook.py
```

The inputs used the same field shapes as the supported Codex Hooks. Each event passed through the installed Python process, loopback HTTP endpoint, Electron main process, IPC boundary, and renderer. Computer Use sampled the installed application's visible state after the events.

A separate real `codex exec` attempt was excluded from the two controlled rounds because the model sampling request timed out and retried four times before cancellation. That attempt is evidence of an external Codex/network delay, not a Blueberry Hook latency measurement.

## Round 1

Sequence:

```text
SessionStart → UserPromptSubmit → PreToolUse → PostToolUse → Stop → SessionEnd
```

All six Python Hook processes exited `0`, wrote exactly `{}`, and left stderr empty. Every visible sample showed Working, including samples after Prompt, Stop, and SessionEnd. Thinking, Happy, and Sleeping could not be observed.

## Round 2

Sequence:

```text
SessionStart → UserPromptSubmit → PreToolUse → PermissionRequest
→ PostToolUse → Stop → SessionEnd
```

| Hook | Python process time |
|---|---:|
| SessionStart | 150 ms |
| UserPromptSubmit | 38 ms |
| PreToolUse | 40 ms |
| PermissionRequest | 39 ms |
| PostToolUse | 41 ms |
| Stop | 39 ms |
| SessionEnd | 39 ms |

All seven processes exited `0`, wrote exactly `{}`, and left stderr empty. The UI again showed Working at every sample, including 1.12 seconds after PermissionRequest and 3.32 seconds after SessionEnd.

A direct canonical event request independently returned HTTP `200` with state `thinking`, while the subsequently observed UI still showed Working. This localizes the user-visible failure after event validation/routing and is consistent with another concurrent Tool Hook overwriting the renderer state.

## Root Cause Evidence

Blueberry v1.1.0 collapses events from every Codex task into one global renderer state. The renderer receives only the visual state string, not the originating session identity, so it cannot arbitrate between tasks.

The current visual policy is also intentionally preemptive:

- Working clears transient timers and hides all action GIFs.
- Attention clears Working and other transient actions.
- Thinking is assigned a random 5–10 second duration, but the next Tool event can replace it before it finishes.
- Both PreToolUse and PostToolUse map to Working; PostToolUse restarts the 30-second Working timeout.
- Happy is protected, and SessionEnd is deferred until Happy finishes, but an unrelated concurrent task can still supply new global events.

Computer Use is itself a Codex tool. Therefore observing Blueberry from the active Codex task produces Tool Hooks and demonstrates the same cross-task collision that users can encounter when more than one Codex task is active. The observer effect limits animation-specific screenshot attribution, but it does not invalidate the product finding: unrelated task activity can overwrite the pet's only visual state.

## Verdict

- **Hook adapter responsiveness:** Pass. Warm event processes completed in 38–41 ms; no evidence points to Python or loopback transport as the main source of perceived lag.
- **Single global state under concurrent activity:** Fail. Two rounds reproduced persistent Working and masked other semantic states.
- **Animation continuity:** Fail for current user expectation. Most actions are deliberately interrupted by newer events rather than queued or allowed to reach a minimum display time.
- **Release recommendation:** Hold the stable v1.1.0 GitHub release until state arbitration and minimum-display behavior are designed and retested. The existing build remains a completed technical MVP, but this test shows it is not yet a reliable multi-task user experience.

## Follow-up Scope to Discuss Before Implementation

1. Decide whether Blueberry represents the latest task, the foreground task, the highest-priority task, or an aggregate of all tasks.
2. Preserve `session_id` through the main-to-renderer boundary so the policy can distinguish event sources.
3. Define minimum display times and interruption rules for Thinking, Attention, Working, Happy, and Sleeping.
4. Separate Tool started from Tool finished instead of mapping both to an identical 30-second Working state.
5. Add deterministic multi-session event-sequence tests before another real-environment acceptance run.
