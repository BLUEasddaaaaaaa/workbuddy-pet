- **Date:** 2026-08-01
- **Result:** BLOCKED

## Scope and Decision

This acceptance checks the lightweight session-aware coordinator, renderer deduplication, renderer-readiness delivery, arm64 packaging, and the installed Codex Hook path. Automated policy and transport checks pass, but the installed renderer can suppress a legitimate repeated state after a local animation timeout has visually returned to Idle. Because Permission feedback is user-actionable, this is a release blocker rather than a cosmetic limitation.

No production code was changed during this acceptance task.

## Blocking Reproduction

1. A unique canonical Permission event was posted to the installed app:

```text
POST /event -> HTTP 200 in 14.655 ms
{"status":"ok","event_id":"evt_acceptdirect001","state":"attention"}
```

2. The immediate installed-app screenshot showed the Idle sprite instead of Attention.
3. A direct diagnostic `POST /state {"state":"attention"}` returned HTTP 200 and produced the question-mark Attention sprite once.
4. After the renderer's five-second Attention timeout restored the visual to Idle, another `POST /state {"state":"attention"}` again returned HTTP 200 but remained visually Idle.

The renderer presentation policy remembers the last externally approved state, while renderer-owned timeouts can change the visible state without updating that policy. It can therefore remember `attention` while the user sees Idle and suppress the next legitimate `attention` as a duplicate. This invalidates the required guarantee that Permission feedback is observable.

### Mandatory original-symptom gate

The original symptom was tested before canonical or multi-session traffic:

1. `POST /state {"state":"attention"}` returned HTTP 200 in **15.930 ms**.
2. Computer Use still showed the Idle sprite instead of the expected Attention visual.
3. Because Computer Use itself can produce Codex Hook traffic, one permitted isolation attempt temporarily moved the installed adapter out of its configured path.
4. With the adapter isolated, the same POST returned HTTP 200 in **4.194 ms**, but Computer Use again showed Idle.
5. The adapter was immediately restored and is byte-for-byte identical to the repository adapter (`cmp` exit 0).

The acceptance gate therefore did not obtain a positive first-Attention observation. The required wait-to-Idle and second Attention replay, Happy replay/sound check, canonical Permission event, two adapter rounds, and overlapping-session runtime sequence were intentionally not run. Continuing would have produced downstream measurements without first proving the user-visible blocker was resolved.

The two-phase actual-visual ledger and renderer-readiness bridge are covered by deterministic tests, but this run did not visually capture the first diagnostic Attention state. Computer Use has both observer-Hook and capture-timing limitations, so this observation does **not** conclusively prove that the Task 3b product fix failed. It does mean the mandatory installed visual proof is absent. A separate debugging task must distinguish IPC delivery, renderer transition execution, asset visibility, capture timing, and other installed-runtime conditions.

## Verdict

**BLOCKED.** The earlier repeated-Attention defect has a tested two-phase visual-ledger fix, and all 90 complete automated tests plus 43 focused checks pass. Nevertheless, the rebuilt installed application did not provide the required positive first-Attention visual evidence, even after one observer-Hook isolation attempt. This blocks acceptance rather than conclusively proving the fix wrong. Keep v1.1.0 stabilization in progress and hold the stable GitHub release until a fresh acceptance proves Attention → Idle → Attention in the installed app.
