# 子 Agent 开发与审查流程

- 只有用户明确批准子 Agent 执行后才能派发；讨论协作方案不等于授权。
- 状态控制器任务串行执行，不允许多个实现 Agent 同时修改共享状态、Renderer、路由或测试文件。
- 每个有边界的任务使用新的实现 Agent，直接提供任务全文、允许和禁止文件、产品规则、测试命令、证据要求与停止条件。
- 实现 Agent 必须使用 TDD：先添加聚焦失败测试并证明失败原因正确，再写最小实现，重跑聚焦与相关回归测试，自查 diff，仅提交授权范围。
- 实现 Agent 返回 `DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT` 或 `BLOCKED`，并报告修改文件、前后测试证据、数量、提交哈希和遗留问题。
- 实现完成后，先由独立规格审查 Agent 检查产品语义、优先级、保护时间、pending、单一权威、范围遗漏和额外行为。
- 规格问题未清零前任务不完成；由原实现 Agent 定点修复，再做规格复审。
- 规格通过后才进行独立代码质量审查，检查状态权威重复、计时器所有权和清理、过期补播、动画重启、测试质量、无关重构和可维护性。
- 质量问题未清零前任务不完成；修复后必须复审。
- 主 Agent 独立检查 Git 状态、完整 diff、`git diff --check`、文件范围、提交身份和真实测试输出，不接受子 Agent 口头结论作为充分证据。
- 所有任务完成双重审查后，使用新的最终审查 Agent 检查完整变更，再由主任务重跑完整自动化和运行验收。
- `NEEDS_CONTEXT` 必须补充已经确认的上下文再派发；`BLOCKED` 必须判断是上下文、能力、任务拆分还是计划本身有问题，不得原样重复尝试。
- 第一次有证据的实现仍失败、出现架构冲突或产品规则歧义时，保存证据并停止所有下游工作，等待用户确认。
