# 测试、验收与证据规则

- 第一次有证据的修复仍失败时，保存失败测试、复现步骤、日志和 Git 状态，停止并询问用户。
- 验收门槛失败后不继续下游测试，不通过削弱、删除或改写验收要求获得 PASS。
- TDD 的失败阶段必须由目标行为缺失引起；实现后运行同一个聚焦测试证明转绿，再运行相关回归。
- 优先使用确定性测试和假时钟验证状态边界；运行态动画使用 CDP 检查 Renderer 状态，Computer Use 不作为并发或精确时间行为的唯一证据。
- HTTP 200 只证明事件被接受；单元测试只证明对应逻辑；截图只证明观察时刻；单轮运行不证明稳定性。
- 主 Agent 必须核对实际命令、退出码、测试数量、跳过项和原始输出。
- 验收脚本中的每一项预期都必须可追溯到当前有效 Agent 规则、实现代码、已有测试或执行前的只读运行探测；证据来源必须在脚本或验收记录中注明。不得根据状态名称、常见约定、其他项目或先前机器环境自行推导 DOM class、图片 ID、命令路径、端口、进程名称或制品结构。
- 编写验收脚本前先生成“预期—依据”检查表并逐项核对。有效规则已有明确映射时以规则为准，同时检查实现是否一致；规则未覆盖时先只读检查实现和运行环境，不得把未经验证的假设写进可执行断言。
- 验收脚本自身失败必须与产品失败分开记录。若失败来自错误断言、工具路径或 Harness 假设，立即停止，保留原始证据；未经用户确认不得修改脚本后连续重跑，也不得据此判定产品失败。
- 轮询样本与成功检查点必须使用不同的数据类型和字段语义：poll 记录每次尝试及 `expectedState`、`actualState`、`matched`；checkpoint 只能在断言实际匹配后生成。独立复核器只能使用明确 checkpoint，不得把 label、数组位置或“最后一个样本”等隐含约定当成通过证据。
- Harness 输出必须包含版本化 schema、原始 fixtures、polls、checkpoints 和可复核 summary；复核器必须独立重算关键结论。任一校验程序的非零退出码必须原样传播，禁止被后续清理或诊断命令覆盖。
- v1.1.0 必须分别通过自动化、worktree 运行时、真实单会话 Codex、安装运行时和制品身份门槛，才能声称完成或发布就绪。
- 多会话行为不属于当前确认的 v1.1.0 范围。
- 已知必需行为失败或缺少证据时，不得使用“完成”“接近完成”“已验收”“可发布”等表述。
